第 12 章 · Part 4：Agent 開發

Agent 架構設計

Agent 架構選型、max_iteration 設定、ReAct 迴圈行為分析與地端模型的 pre_prompt 工程最佳實踐。

一、雙語 Agent 架構選型與重構

在開發跨國或多語言應用的 AI Agent 時，最直覺的想法是「建立一個通用的 Agent，讓它在同一個 System Prompt（Pre-prompt）中同時處理中英文對話」。然而，實務上這種混合架構會帶來顯著的缺點：

  • 指令干擾與混亂：模型容易混淆中英文的輸出規則，例如要求它用中文回答時吐出英文，或是在輸出格式中混入另一種語言的標籤。
  • Token 浪費：在 Pre-prompt 中寫入兩套語言的防禦規則，會佔用大量無效的 Token，拉高推理成本並拖慢反應速度。
  • 髒輸出污染：模型更容易把 pre-prompt 中的語言鎖定指令（例如 [LANGUAGE INSTRUCTION: always reply in...]）抄進 Final Answer 中一併回吐給用戶。

💡 最佳實踐：雙金鑰路由架構

最乾淨且穩定的重構設計是「分拆為兩個獨立的 Dify App（中文版 Agent 與英文版 Agent），並在 Gateway 閘道層（如自建的 login-app）進行路由」：

  1. 在 Dify 後台建立兩個 App，其 Pre-prompt 分別寫死「強制繁體中文」與「強制英文」。
  2. 資料庫為同一個業務專案儲存兩套 API Key（如 api_key_zh 與 api_key_en）。
  3. 當前端使用者傳入請求時，Gateway 依據用戶當前的語系（Language）自動調用對應的 API Key 轉發給 Dify。這樣可以將語言鎖定的責任完全從 API 呼叫鏈中剝離，讓 Agent 的 Pre-prompt 保持極度純粹。

二、ReAct 迴圈行為分析與 max_iteration

當我們在自架地端使用較弱的模型（如 7B 到 20B 參數規模的模型，或是未經過嚴格 ReAct 微調的模型）時，最常遇到的問題是：第一次查詢沒有表格或答案，必須問第二次才正常。

透過 Dify Logs 進行分析，會發現這是因為模型陷入了 ReAct 迴圈的「終止難題」：

在 ReAct 機制中，模型必須在獲得工具的 Observation: 後，判斷資訊足夠並輸出 Final Answer: 來結束對話。然而弱模型在讀取到 Observation 後，往往會失去對上下文的控制，繼續輸出 Thought 或 Action，反覆呼叫同一個工具，直到觸發 Dify 的 max_iteration（最大疊代次數）限制被強制中斷。由於是被系統強行切斷，最終返回給用戶的 answer 欄位只能留空。

🛠️ 解法：依模型等級合理配置 max_iteration

模型規模 建議 max_iteration 值 設計策略
地端弱模型（7B ~ 20B） 3 限制迴圈次數，避免重複調用同一工具，並強迫其盡快結束。
地端強模型 / 雲端模型（70B+） 5 ~ 6 模型有足夠的推理能力，可給予較多次數以應付複雜的多步驟工具鏈。

動態熱更新 Agent 配置 (CLI 腳本)

在頻繁調校 `max_iteration` 或 `pre_prompt` 的階段，手動登入 Dify UI 修改會大幅降低效率。我們可以透過自製的 Python 腳本直接調用 Console API，在終端機中實現一鍵熱更新（Hot Update）：

PowerShell

PS> python scripts/dify_agent_update.py --app_id 8b9f...4a21 --max_iteration 3

三、Pre-prompt 工程：三項防禦性設計規則

為了徹底根治地端模型在 ReAct 模式下的「工具名稱幻覺」與「迴圈不終止」，我們必須在 System Prompt（Pre-prompt）中寫入防禦性規則（Defensive Prompting）。以下是經過實戰驗證的三大核心防線：

Dify Agent Pre-prompt 防禦規則範例 
0. **資料即時性原則（最高優先）**：
   每一輪提問都必須重新呼叫對應 MCP 工具取得最新資料。
   嚴禁引用對話歷史中先前的 Observation 或 Final Answer。

1. **單次呼叫與強制終止原則**：
   每次提問僅能呼叫一次工具。
   ⚠️ TERMINATION MANDATE: 收到 `Observation:` 的瞬間，下一個輸出「必須」是 `Final Answer:`，不得再寫任何 `Thought` 或 `Action`。

4. **工具名稱與 Schema 真實性（防幻覺，強制）**：
   - `tsc_mcp` 唯一允許的工具名稱為：`create_amr`、`list_amr`、`get_amr`、`update_amr`、`delete_amr`、`list_alarm_codes`、`get_alarm_levels`。**嚴禁自創或改寫工具名稱**。
   - `list_amr` 與 `get_amr` 回傳僅有三個欄位：`id`、`vehicle_no`、`battery`。系統中不存在 `status`、`position` 等欄位，嚴禁虛構。

1. Rule 0：資料即時性原則（最高優先）

如果沒有寫入此規則，模型會傾向於使用前幾輪對話記憶（Conversation History）中的舊數據來回答，而不會真的去呼叫 MCP 工具。這會造成資料不即時或完全對不上。此規則能強制模型每一輪都去打工具拿最新資料。

2. Rule 1：單次呼叫與強制終止（TERMINATION MANDATE）

這條規則是為了解決上述「迴圈不終止」的狀況。它直接命令模型在看到 Observation: 的下一個 Token 必須是 Final Answer:。這能引導模型不繼續推理，立刻給出答案。

3. Rule 4：工具名稱與 Schema 真實性（Tool Grounding）

這是一項關鍵的防幻覺（Anti-Hallucination）技術。地端模型因為訓練集中有大量的其他工具調用範例，當遇到自訂工具時，模型會開始「語意聯想」並自創工具名稱（例如將 list_amr 寫成 list_amr_devices），或是自己虛構不存在的資料表欄位（例如欄位只有 id, battery，卻在表格中虛構 status, position）。

透過「白名單列舉允許工具」與「強制定義回傳 Schema 欄位」，能有效鎖死模型行為，杜絕幻覺發生。

四、不同模型的 Pre-prompt 適應性對照

防禦性 Prompt 並不是藥到病除的萬靈丹，不同規模與架構的模型對這些規則的適應性各不相同：

模型 TERMINATION MANDATE 適應性 工具呼叫防幻覺表現
gpt-oss-20b ✅ 非常有效。加了 few-shot 範例後，能顯著降低 ReAct 陷入死循環的機率。 需要 Rule 4 嚴格列舉工具與欄位，否則極易產生名稱幻覺。
gpt-oss-120b ⚠️ 容易被干擾。由於是大型推理模型，如果加入太多 ReAct few-shot 文字，反而會干擾其內置的解析，導致輸出空白。建議不加 two-shot，僅寫精簡規則。 表現優異，使用原始 Prompt 與 Schema 即能正確呼叫，不太需要特別限制。
llama-4-maverick ✅ 有效，能引導其快速輸出。 對自訂工具需要 Rule 4 的限制，否則仍會傾向使用其訓練集中的常見工具名。
💡
調優核心邏輯

如果您的 Agent 持續出現 Observation Observation 的髒輸出、工具重複呼叫或格式跑掉，在經過一兩次 Prompt 微調無效後，「升級模型」通常會比繼續修改 Prompt 更划算、更省時。例如從 20B 級升級至 32B 級或 70B 級，往往能以物理性能壓制這些邏輯錯誤。
