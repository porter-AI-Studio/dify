第 10 章 · Part 3：Workflow 設計

大型 Schema 架構策略

在面對只有十幾張資料表的小型資料庫時，將全量 Schema 硬編碼（Hardcode）寫入 System Prompt 是最穩妥的做法。但當資料庫規模擴大至數十甚至數百張表時，爆 Token 與多餘欄位干擾將會使 NL2SQL 精確度雪崩式下跌。本章將深度探討大型資料庫的 Schema 架構策略。

一、為什麼不能無限 Hardcode？

在設計 NL2SQL 時，提供給 LLM 越多無關的資訊，並非精確度越高，反而容易引發幻覺：

方案 A：全量 Schema 注入 (Full Schema) 表數量 ≤ 20

做法： 將所有表格定義直接寫死在 System Prompt 裡。
優點： 結構最簡單，精確度最高，不會漏掉關聯表。
缺點： 消耗約 1,000 Tokens，當表擴增時會迅速拖慢推理速度。

方案 B：RAG 語意檢索 (Schema Retrieval) 表數量 30 ~ 100

做法： 將每張表的 Schema 存入 Weaviate 等向量資料庫，依據使用者提問，動態檢索最相關的 Top K 張表注入。
缺點： 依賴 Embedding 模型的語意理解，若是跨多表的複雜 JOIN，極易因為向量相似度不足而漏抓關鍵表，導致 SQL 報錯。

方案 C：兩階段選表架構 (Two-Stage Pipeline) 表數量 100+

做法： 第一階段，只給 LLM 所有表格的「名稱與中文簡介」，讓 LLM 輸出真正需要的表格清單（如 ["orders", "products"]）；第二階段，利用程式碼節點精準提取這幾張表的完整 DDL，再餵給生成 SQL 的主模型。
優點： 完美解決 Token 浪費與無關欄位的噪聲干擾，是大型資料庫的最優解！

⚠️
不相關表的「噪聲干擾」

若 LLM 同時看到 50 張表，當使用者問「查詢各員工負責的訂單金額」時，LLM 可能會把 employee_salary 中的金額或 freight 運費欄位混淆進去。資訊越精簡，生成的 SQL 越精準。

二、方案 B：RAG Schema 檢索 (30 ~ 數百張表)

當表數量處於 30 至數百張時，最直覺的做法是動態選表：將每一張資料表的 Schema 當作獨立的 Markdown 文件，匯入 Dify 知識庫。當使用者提問時，系統會先對知識庫進行向量搜尋（Semantic Search），僅將命中的表結構動態注入 Prompt 中。

1. 知識庫 Markdown 文件規格（每表一檔）

knowledge/products.md 
## products（產品表）
用途：儲存商品基本資訊、定價、庫存。
常見查詢關鍵字：商品、貨品、品項、定價、庫存、停產
關聯：supplier_id -> suppliers；category_id -> categories

| 欄位 | 型別 | 說明 |
|---|---|---|
| product_id | smallint PK | 產品 ID |
| product_name | varchar(40) | 產品名稱 |
| unit_price | real | 單價 |
| units_in_stock | smallint | 庫存數量 |
| discontinued | integer | 是否停產（0/1）|

2. Dify 工作流編排與 Prompt 改寫

在 Dify Chatflow 中，您只需在 LLM 之前串接一個 Knowledge Retrieval（知識檢索） 節點，並將 LLM 節點的 System Prompt 修改為引用檢索變數：

RAG LLM System Prompt 
你是 SQL 工程師，根據以下「已檢索到的相關資料表結構」生成 SQL：

{{#context#}}

⚠️ 只能使用上方出現的資料表與欄位，禁止憑感覺推測。
（其餘 Guidelines 保留不變）
  • 優點：極低 Token 消耗、易於建置。
  • 缺點：存在 RAG 語意搜尋 Miss 的風險（例如：當問題缺少明確關鍵字時，可能漏掉必要的 JOIN 關聯表）。

三、方案 C：兩階段 Pipeline 架構 (100 張表以上)

針對數百張表的大型企業級資料倉儲，RAG 的模糊比對可能無法保障 100% 關聯精確度。此時，我們必須採用 **兩階段 Pipeline（Two-Stage Pipeline）** 機制。核心哲學是將「選取表格」與「生成 SQL」拆分為兩個獨立任務：

Stage 1

Table Selector (選表)

僅輸入「所有表名 + 單行說明」，讓 LLM 推理並輸出所需的 JSON 陣列。

→
Code Node

Schema 組裝

以 Python/JS 節點過濾，從 Dictionary 中精確取出該幾張表的完整定義，組裝為 Context。

→
Stage 2

SQL Generator (生成)

輸入僅含命中的幾張表之完整 Schema，精確生成無污染的 SQL。

1. Stage 1 Prompt（選表階段）

Stage 1 Prompt 範例 
你是資料庫專家。根據使用者問題，從下方清單選出
「生成 SQL 所需的資料表」，僅回傳 JSON 陣列，不需解釋。

資料表清單：
- employees：員工基本資料（姓名、職稱、主管）
- orders：訂單紀錄（日期、客戶、員工、運費）
- order_details：訂單明細（產品、數量、單價、折扣）
- products：產品（名稱、定價、庫存、分類）
- customers：客戶（公司名稱、聯絡資訊、國家）
...（共 100 張表，每張只需一行說明）

使用者問題：查詢 2003 年各員工負責的總訂單金額，並按金額由高到低排序

2. Code 節點 Schema 組裝（Python 實作）

Code 節點組裝代碼 
# SCHEMA_STORE 預先存放所有表格的欄位說明
SCHEMA_STORE = {
    "employees": "- employees: employee_id (PK), last_name, first_name, title, hire_date, reports_to (FK)",
    "orders":    "- orders: order_id (PK), customer_id (FK), employee_id (FK), order_date (date), freight",
    "order_details": "- order_details: order_id (FK+PK), product_id (FK+PK), unit_price (real), quantity (smallint), discount (real)",
    # ... 其餘上百張表
}

# 根據 Stage 1 (Table Selector) 回傳的 JSON 陣列進行過濾組裝
import json
selected_tables = json.loads(input.selected_tables_json)
schema_text = "\n".join(SCHEMA_STORE[t] for t in selected_tables if t in SCHEMA_STORE)

3. Stage 2 Prompt（生成階段）

Stage 2 Prompt 範例 
你是 SQL 工程師，根據以下資料表結構生成 SQL：

- employees: employee_id (PK), last_name, first_name ...
- orders: order_id (PK), employee_id (FK), order_date ...
- order_details: order_id (FK+PK), unit_price, quantity, discount

問題：查詢 2003 年各員工負責的總訂單金額，並按金額由高到低排序
  • 優點：精確度極高，選表準確度遠超 RAG 語意比對。
  • 缺點：需呼叫兩次 LLM，延遲增加 1~2 秒，且 Chatflow 編排較複雜。

四、決策矩陣與升級路徑

以下是針對不同資料庫表數量的架構抉擇建議：

資料表數量 推薦方案 Dify 工作流改動量
≤ 20 張 方案 A (Hardcode 全量) 無改動（最省心）。
20 ~ 100 張 方案 B (RAG 檢索) 將 Schema 上傳知識庫，加一個知識檢索節點。
100 張以上 方案 C (兩階段 Pipeline) 需重構 Chatflow，編排兩組 LLM 與 Code 節點。

五、RAG 知識庫防漏 (Miss) 最佳實踐

若您採用方案 B（RAG 檢索），我們提供以下優化指南來降低選表遺漏的機率：

  1. 知識庫 Chunk 分割策略：強烈建議採用「一表一文件」的檔案管理方式。若有多張表放在同一個 .md，分割設定務必選擇「依標題分割 (\\n##)」，確保檢索出的 Chunk 是一個完整的資料表，而不會產生切斷的情形。
  2. 添加同義詞 (Synonyms)：在每張表的 Markdown 首段，加入「常見查詢關鍵字」欄位（如 products 加上「貨品、商品、定價、停產」），大幅提升語意向量檢索的命中率。
  3. 固定核心表（混合模式）：對於幾乎所有查詢都會用到的核心表（例如 orders 或 users），可以直接 Hardcode 寫死在 LLM 的 System Prompt 中；僅讓 RAG 檢索去動態匹配補充的業務表。
