第 13 章 · Part 4：Agent 開發

Console API 自動化操控

透過 Dify Console API 直接修改 Agent、Chatflow、Workflow，實現無需 DSL 匯出入的程式化管理。

一、為什麼需要自動化操控 Console API？

Dify 官方提供的「應用 API（App API）」主要用於對話、工作流執行與知識庫檢索，但**完全沒有提供「修改應用設定（如修改 Prompt、更換模型、調整參數）」的 API**。

在實際開發與運維中，手動開啟瀏覽器進入 Dify 畫布去更改設定有幾個重大的痛點：

  • 無法整合進 CI/CD 流水線進行自動化測試與部署。
  • 當有多個雙語 Agent 需要做全局的 System Prompt 熱修復（Hotfix）時，手動操作耗時且容易遺漏。
  • 難以進行自動化版本控制（備份與回滾）。

為此，我們可以繞過標準 API，直接調用 Dify 網頁後台使用的 Console API（控制台 API），實現在本機端或 CI 腳本中以程式化（Programmatic）的方式直接管理與修改您的 Agent 或工作流配置，甚至無需進行繁瑣的 DSL 匯出與匯入。

二、Dify Console 認證原理

要成功呼叫 Console API，必須正確模擬 Dify Web 控制台的認證流程：

  1. 登入認證：向 POST /console/api/login 發送登入請求。請特別注意：傳入的密碼必須經過 Base64 編碼（非明文，亦非 RSA 密鑰），否則會被攔截並返回 401 Invalid encrypted data 錯誤。
  2. Session 保持：Dify 使用 Cookie 來儲存 access_token、refresh_token 等身分憑證。在編寫腳本時，必須使用可保存狀態的 HTTP 客戶端（例如 Python 的 requests.Session，或是在 urllib 中加入 CookieJar），確保後續請求都會帶上對應的憑證 Cookie。
  3. CSRF 防護標頭：這是最容易踩坑的防線。在登入成功後，必須從 Cookie 中提取 csrf_token 的值，並在之後的所有寫入請求（POST/PUT/DELETE）中，手動加入以下自訂 Header： 
    X-CSRF-Token: <您的 csrf_token 值>
    ⚠️ 標頭的名稱必須是 X-CSRF-Token（有連字號），寫錯成 X-CSRFToken 會導致 401 拒絕。

import
requests, base64

session = requests.Session()
# 1. 密碼 Base64 編碼
pwd_b64 = base64.b64encode(
b"my_password"
).decode()

# 2. 登入取得 Cookie
session.post(
"http://.../login"
, json={
  
"email"
:
"admin@a.com"
,
"password"
: pwd_b64
 })

# 3. 提取 csrf_token
csrf = session.cookies.get(
"csrf_token"
)
session.headers.update({
"X-CSRF-Token"
: csrf})

三、Console 常用 API 端點對照

在進行腳本編寫前，請先查閱下表確認各動作對應的正確 HTTP 方法與 URL：

動作 方法 API 端點 說明與注意事項
登入 POST /console/api/login 密碼需 Base64 編碼，用以獲取 session Cookie。
列出所有 App GET /console/api/apps?page=1&limit=100 獲取所有專案的 UUID、mode（類型）與名稱。
獲取 App 設定詳情 GET /console/api/apps/{app_id} 返回 App 的完整資料，其 model_config 即為 Agent 設定。
更新 Agent 配置 POST /console/api/apps/{app_id}/model-config 整包更新（System Prompt、工具白名單、模型參數）。
獲取 Workflow 草稿 GET /console/api/apps/{app_id}/workflows/draft 返回當前的 Draft Graph 節點與連線。
更新 Workflow 草稿 POST /console/api/apps/{app_id}/workflows/draft 更新草稿圖。
發布草稿 POST /console/api/apps/{app_id}/workflows/draft/publish 將草稿同步為正式版，前台用戶此時才能看到變更。
⚠️
常見端點誤區

如果您發送 GET /console/api/apps/{app_id}/model-config，系統會返回 405 Method Not Allowed。因為 model_config 資料在 Dify 設計中是直接內嵌於「App 詳情」的回應裡。正確做法是 GET 應用詳情，將其取出來修改，再 POST 回去更新。

四、實戰：Python 查詢 App UUID 對照表

在自動化部署或資料庫更新中，您常常需要獲取各專案的 UUID。以下提供一個不依賴第三方庫、僅使用 Python 標準庫實現登入並獲取對照表的實用腳本：

list_dify_apps.py 
import urllib.request
import json
import base64
import http.cookiejar

DIFY_BASE = 'http://localhost'
EMAIL = 'porteryen@gmail.com'
PASSWORD = 'admin5613686'  # 實際環境中請從環境變數讀取

cj = http.cookiejar.CookieJar()
opener = urllib.request.build_opener(urllib.request.HTTPCookieProcessor(cj))

# 1. 登入（密碼須經過 Base64 編碼）
b64pwd = base64.b64encode(PASSWORD.encode()).decode()
login_data = json.dumps({
    'email': EMAIL,
    'password': b64pwd,
    'language': 'zh-Hans',
    'remember_me': True
}).encode()

req_login = urllib.request.Request(
    f'{DIFY_BASE}/console/api/login',
    data=login_data,
    headers={'Content-Type': 'application/json'}
)
with opener.open(req_login) as r:
    pass  # CookieJar 會自動保存 access_token 與 csrf_token

# 2. 從 Cookie 取得 CSRF Token
csrf = next((c.value for c in cj if c.name == 'csrf_token'), '')

# 3. 呼叫 Console API 獲取 App 清單
req_apps = urllib.request.Request(
    f'{DIFY_BASE}/console/api/apps?page=1&limit=100',
    headers={'x-csrf-token': csrf}
)
with opener.open(req_apps) as r:
    apps_data = json.loads(r.read()).get('data', [])

# 4. 輸出 UUID 對照表
for app in apps_data:
    print(f"{app['id']} | {app['mode']:<16} | {app['name']}")

五、Console API 的修改策略與防錯

為了確保自動化修改的安全性，請在執行腳本時遵守以下規範：

  • 修改前必做備份：在呼叫 POST 覆寫 model_config 或 draft 前，腳本應先將 GET 出來的 JSON 設定存入本地備份資料夾（如命名為 [AppName]_backup_[timestamp].json）。一旦修改出錯導致畫布連線斷開，可在第一時間將備份 JSON 覆寫回去。
  • 禁止繞過 API 直接修改資料庫：雖然在 PostgreSQL 中直接使用 SQL 修改 apps 或 workflows 表非常簡單，但由於 Dify 內部（尤其是 Redis 與 Gunicorn）有高度的快取機制，直接更新 DB 會導致快取與資料庫不一致，從而引發應用狀態腐化。必須一律通過 Console API 進行修改。
  • 更新後清理 Cache 驗證：當更新了 Agent 的 Prompt 或模型參數後，在前端進行測試前，**務必清除該對話（Conversation）的 Session**，防止快取中的歷史上下文污染新版本的指令效果。
