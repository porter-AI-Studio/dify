第 11 章 · Part 3：Workflow 設計

Chatflow 對話流程設計

設計可維護的 Chatflow 架構，包含 Draft Graph 讀寫、節點修改、Draft 發布流程與常見修改範例。

一、什麼是 Chatflow？

在 Dify 中，工作流系統被拆分為兩種類型：Workflow（工作流） 與 Chatflow（對話流）。

雖然兩者的底層引擎都使用相同的節點連線圖（Graph），但其設計目的截然不同：

  • Workflow：單次觸發的 Pipeline（單向輸入 $\rightarrow$ 處理 $\rightarrow$ 輸出）。它沒有對話歷史記憶（Conversation History），通常做為 API 或背景任務使用。它的起點是 Start 節點，終點是 End 節點。
  • Chatflow（Dify 模式值：advanced-chat）：專門為聊天場景設計的多輪對話工作流。它會自動維護對話歷史，適合用來開發複雜的對話 Agent 或問答助手。它的起點是 Start，但其核心是透過 Answer 節點將結果串流返回給用戶。

二、Chatflow 核心架構：Graph 與 Draft 機制

一個 Chatflow 的核心邏輯主要儲存於 Workflow Graph，包含節點（Nodes）與連線（Edges）兩大部分。另外會搭配一個 model_config 儲存基礎設定（如開場白、推薦問題等）。

為了防止開發中的變更直接影響到線上用戶，Dify 引入了「草稿（Draft）」與「發布（Publish）」的分離機制：

  1. 在畫布或透過 API 做出的所有修改，都會先寫入 Draft Graph（草稿）。
  2. 當修改完成並通過驗證後，必須顯示發布，將草稿同步到 Published Graph（正式版），此時前台用戶才能看到最新的對話邏輯。
Dify Draft Graph 結構範例 
{
  "id": "draft-uuid-12345",
  "graph": {
    "nodes": [
      {
        "id": "node-llm-1",
        "type": "llm",
        "data": {
          "model": { "provider": "openai", "name": "gpt-4o" },
          "prompt_template": [{ "text": "你是一個助理。" }]
        }
      },
      {
        "id": "node-answer-1",
        "type": "answer",
        "data": { "answer": "{{#node-llm-1.text#}}" }
      }
    ],
    "edges": [
      {
        "id": "edge-1",
        "source": "node-llm-1",
        "target": "node-answer-1"
      }
    ]
  }
}

三、Chatflow 常用節點與職責

在規劃 Chatflow 時，合理分配各節點的職責，能大幅降低流程的複雜度。以下是 Chatflow 的常用節點類型：

節點類型 關鍵 Data 欄位 設計職責與最佳實踐
start variables: [] 定義用戶輸入與全局系統變數（如 user_query）。
answer answer: string Chatflow 特有節點。用於向用戶輸出對話內容，支援 Markdown，並可串流（Stream）輸出。
llm model, prompt_template 調用語言模型進行推理、判斷或提取。
knowledge-retrieval dataset_ids, retrieval_mode 檢索知識庫（向量庫），將相關文本片段（Chunks）引入上下文。
code code, code_language 使用 Python 或 JavaScript 處理複雜的資料過濾、JSON 解析或格式轉換。
http-request url, method, body 呼叫外部第三方 API 進行資料串接。
if-else conditions 條件分支判定，引導對話走向不同的處理路徑。
template-transform template 使用 Jinja2 語法對變數進行格式化組裝，常用於排版輸出給用戶看。

四、Console API 自動化修改與發布

在持續整合（CI/CD）或批量維護的場景中，手動開啟 Dify 網頁畫布去調整 Prompt 或切換模型非常沒有效率。Dify Console 提供了一套內部 API（即網頁後台使用的接口），允許我們編寫腳本來自動讀取、修改並發布 Chatflow 流程圖，免除匯出與匯入 DSL 的繁瑣步驟。

1. 認證原理與 Header 配置

Console API 的認證需要模擬網頁登入，取得 Cookie 中的 csrf_token，隨後在所有 POST/PUT 請求中帶上 X-CSRF-Token 標頭。密碼在登入時必須經過 Base64 編碼。

2. 自動化腳本範例

以下 Python 腳本展示了如何登入 Dify 後台、取得指定 Chatflow 的 Draft Graph、修改特定 LLM 節點的 Prompt，隨後更新並將其發布上線：

scripts/dify_direct_modify.py 
import requests
import base64

DIFY_BASE = 'http://localhost'
EMAIL = 'porteryen@gmail.com'
PASSWORD = 'admin5613686'  # 從 .env 中讀取
APP_ID = 'your-app-uuid'

session = requests.Session()

# 1. 登入（密碼需 Base64 編碼）
login_payload = {
    'email': EMAIL,
    'password': base64.b64encode(PASSWORD.encode()).decode(),
    'language': 'zh-Hans',
    'remember_me': True
}
login_resp = session.post(f'{DIFY_BASE}/console/api/login', json=login_payload)
login_resp.raise_for_status()

# 2. 取得 CSRF Token
csrf_token = session.cookies.get('csrf_token', '')
headers = {
    'X-CSRF-Token': csrf_token,
    'Content-Type': 'application/json'
}

# 3. 取得 Draft Graph
draft_url = f'{DIFY_BASE}/console/api/apps/{APP_ID}/workflows/draft'
draft_resp = session.get(draft_url, headers=headers)
draft_resp.raise_for_status()
draft_data = draft_resp.json()
graph = draft_data['graph']

# 4. 修改特定 LLM 節點的 Prompt
for node in graph['nodes']:
    if node['type'] == 'llm' and node['id'] == 'node-llm-1':
        node['data']['prompt_template'][0]['text'] = '全新的助理 Prompt 指令。'

# 5. 更新 Draft
update_resp = session.post(draft_url, json={'graph': graph}, headers=headers)
update_resp.raise_for_status()

# 6. 發布生效
publish_resp = session.post(f'{draft_url}/publish', headers=headers)
publish_resp.raise_for_status()
print("Chatflow 修改並發布成功！")
⚠️
認證與 Header 踩坑點

1. 登入 API（/console/api/login）傳入的密碼必須先做 Base64 編碼，否則會返回 401 Invalid encrypted data 錯誤。
2. 後續請求的 Header 名稱為 X-CSRF-Token（有連字號），寫錯成 X-CSRFToken 會導致權限拒絕。

五、設計最佳實踐與防錯機制

在設計與維護 Chatflow 對話流程時，應遵循以下工程化準則：

1. 禁止直接修改 Dify 後台資料庫

雖然可以直接透過 SQL 指令更新 PostgreSQL 中 workflows 表的 graph 欄位，但這樣做會繞過 Dify 的內部快取機制（如 Redis），導致畫布與實際執行版本不一致，甚至腐化 App 的內部狀態。所有自動化修改應嚴格通過 Console API 進行。

2. 修改前備份機制

在呼叫 API 更新 Draft 之前，應將讀取出來的原始 Graph JSON 備份在本地（例如寫入一個時間戳記備份檔），確保若腳本邏輯寫錯或節點意外斷開時，能有完整的回滾（Rollback）路徑。

3. 重置對話記憶以進行驗證

修改完 Chatflow 的 LLM 提示詞或 if-else 分支邏輯並發布後，在調用 API 進行測試時，**務必清除該對話的歷史記憶（重置 Session）**。否則舊的上下文回覆依然會留在 Redis 快取中，污染新的測試結果。

4. Raw Data 輸出策略

與 Agent 類似，Chatflow 中調用的 HTTP 工具或自定義代碼節點，**應盡量回傳原始 JSON 資料**。避免在 API 層級預先將資料排版成 HTML 或複雜的 Markdown 表格。把「組裝排版」的職責留給下方的 Template Transform（Jinja2）節點或 LLM 節點來處理，這樣節點的重用性最高且最穩定。
