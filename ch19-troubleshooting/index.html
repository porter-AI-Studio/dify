第 19 章 · Part 6：最佳實踐

故障排除彙整

彙整 Dify 地端部署、模型註冊、LINE Flex 整合、與 Windows Docker 非對稱路由（Asymmetric Routing）等四大天坑的故障排除經驗。

一、Windows Docker 非對稱路由天坑 (Asymmetric Routing)

在 Windows 宿主機使用 Docker Desktop 運行 Dify 時，若要將模型供應商指向另一個子網路的地端推理服務（例如 LiteLLM 端點 http://192.168.40.203/litellm），通常會出現 **Connection Timeout（連線逾時）** 錯誤。

1. 故障根因

這是一個經典的網路路由問題：非對稱路由（Asymmetric Routing）。

  • Dify Docker 容器的 IP 是虛擬的私有網域（例如 172.x.x.x）。
  • 當容器向 192.168.40.203 發送請求時，封包能順利通過 Windows 網卡與路由器送出。
  • 然而，當目的主機 192.168.40.203 嘗試回傳響應封包給 172.x.x.x 時，由於它不知道這個 Docker 虛擬 IP 的路由路徑，回程封包在路由器端會被直接丟棄，進而導致 Dify 報出 Timeout。

2. 診斷對照

連線路徑 結果 說明
Windows Host (192.168.0.50) ──> LiteLLM ✅ 正常 (HTTP 200) Host 與目的主機同屬局網，路由可達。
Docker 容器 ──> 宿主機 Gateway (host.docker.internal) ✅ 正常 (HTTP 307) 容器到 Host 的內網通道正常。
Docker 容器 ──> LiteLLM (192.168.40.203) ❌ Timeout 回程路由丟失（非對稱路由）。

3. 解決方案：Windows netsh portproxy 轉址

我們利用 Windows 內建的 Port Proxy 功能，將發往 Windows 宿主機特定 Port 的流量轉發給 LiteLLM。這樣一來，Docker 容器只需連線至 host.docker.internal，流量會被 Host 轉發，且來源 IP 會被自動 NAT 轉為 Host 的局網 IP（192.168.0.50），確保回程路徑暢通：

PowerShell (以管理員執行) 
# 系統管理員權限打開 PowerShell 執行
netsh interface portproxy add v4tov4 `
  listenaddress=0.0.0.0 `
  listenport=18080 `
  connectaddress=192.168.40.203 `
  connectport=80

# 驗證轉址設定是否生效
netsh interface portproxy show all

Dify 節點配置：

  • API Endpoint URL 改填：http://host.docker.internal:18080/litellm/v1。
  • Model name for API endpoint：必須與 LiteLLM 上的 Model ID 一致，不可留空。若留空，Dify 會將 Model Display Name 傳過去，導致 Model Not Found 錯誤。

二、Dify 模型註冊與配置四大天坑

在 Dify Console 中新增自訂模型時，經常因為操作順序不對導致功能殘缺：

  • 授權名稱 30 字元限制：填入過長名字（如 nvidia-NIM_meta/llama-4-maverick）會觸發 ParserCreateCredential 錯誤。對策：授權名稱填短名（如 NIM-Maverick），完整路徑寫在 Model Name 欄。
  • Context Size 預設 4K 陷阱：若在註冊模型時沒有滑到對話框最底部填寫 Model context size，Dify 會預設為 4K。這會導致長對話時文本被截斷。
  • Function Calling 預設 Not Support：若未在新增時滑到底部將 Function calling 從 Not Support 改為 Tool Call，Agent 設計頁面的 Strategy 下拉選單將**永遠看不到** Function Calling 選項，只能用 ReAct。
  • 新版 Dify「配置」參數鎖死：特別注意！上述所有特徵參數（Context size、Function calling、Vision 等）在模型建立後，無法透過「配置」按鈕進行修改（配置僅能修改憑證與憑證綁定）。**唯一的補救手段是刪除模型並重新註冊**。

三、LINE Flex Message 整合天坑

在整合 flex-api 與 LINE 機器人時，最常遇到 LINE 平台返回 A message (messages[0]) in the request body is invalid 的 400 錯誤。排查步驟與對策如下：

  1. Contents 雙重嵌套錯誤：flex-api 資料庫內儲存的 JSON 模板**僅應包含核心 contents（如 carousel 或 bubble 物件）**。如果在資料庫裡就包了 "type": "flex"，而 Dify 的 assemble 節點又包裝了一次 "type": "flex"，就會導致 LINE 格式驗證失敗。
  2. Pydantic 序列化產生的 additionalProp1 髒資料：如果使用 FastAPI + Pydantic 的 response_model 自動序列化，格式不對時會在 JSON 最外層多包一層 additionalProp1。最穩健的修復法是直接在 MySQL 中執行 DELETE，然後以純 SQL INSERT 乾淨的 JSON 內容。
  3. HeidiSQL 安全性限制：HeidiSQL 連接自架 MySQL 容器時，主機名稱必須使用 localhost（Port 13366）。且在 Advanced 標籤中務必加入 allowPublicKeyRetrieval=true 並關閉 SSL。

四、Dify DSL 變數型別天坑

在 Dify 工作流中，如果使用了 Code 節點（JavaScript/Python）來清洗上游 LLM 生成的內容（例如 NL2SQL 的 SQL 生成），經常會拋出 TypeError: text.lastIndexOf is not a function 錯誤。

  • 根因：Dify 工作流在將 llm.text 傳入 Code 節點時，特別是針對具有思考區塊的推理模型，傳入的往往不是 primitive string（原始字串），而是一個 Dify 內部的 **Object Wrapper**。即使在 Code 節點中呼叫 String(llm_text)，也只會得到 "[object Object]" 字串，傳給 SQL 執行就會報 SQL 語法錯誤。
  • 對策：盡可能遵守「最簡原則」。在 LLM 節點的 System Prompt 尾端寫入嚴格的 Output 規則（例如：只輸出 SQL，禁帶 markdown 標籤與前言），直接將 llm.text 串接給下游的 SQL 工具節點，**完全跳過 Code 節點進行清洗**。這能顯著降低型別出錯率。
