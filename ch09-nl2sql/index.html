第 9 章 · Part 3：Workflow 設計

NL2SQL 工作流實戰

將使用者的自然語言提問自動轉換為 SQL，連接關聯式資料庫查詢並即時回覆（NL2SQL），是企業 AI 工作流最火熱的應用。本章將手把手教您如何利用最簡原則編排出一條強固的資料庫查詢 Pipeline。

一、NL2SQL 工作流架構：最簡原則

在設計 NL2SQL 工作流時，初學者常犯的錯誤是：在 LLM 之後塞入多個 JavaScript/Python (Code) 節點來「清洗」SQL 語句（例如清除 Markdown 標籤 ```sql）。然而，節點越多，系統的脆弱性就越高。

💡
最簡原則 (Simplicity First)

只要 LLM 的 System Prompt 設定得當，我們可以直接讓推理模型輸出 100% 乾淨的 SQL 語句，並直接送往資料庫查詢工具，完全不需要中間的 Code 節點進行後處理。這能顯著降低運行期型別出錯的風險。

二、LLM 節點設定

1. 模型選擇與參數調整

SQL 生成屬於需要嚴謹推理的任務，因此建議選擇高推理能力的模型，例如 openai/gpt-oss-120b（透過 OpenAI API 相容協定接入的地端模型）或雲端的 gpt-4o / claude-3-5-sonnet。

特別注意：為了確保 SQL 生成的穩定性與一致性，務必將 Temperature 調降為 **0**，避免模型產生過多的創造性發散：

Completion Parameters 
model:
  completion_params:
    max_tokens: 4096
    temperature: 0       # 設定為 0，確保 SQL 穩定一致
  mode: chat
ℹ️
Reasoning Model 的自動分離機制

若使用地端具備思考區塊的推理模型（如 DeepSeek-R1 系列），其輸出的文字會包含 <think>...</think>。幸運的是，Dify 在 LLM 節點層已會自動過濾並分離思維鏈，llm.text 輸出的變數僅會包含最終的乾淨回答，無需下游手動清洗。

2. System Prompt 關鍵輸出規則

為使 LLM 輸出無雜質的 SQL，必須在 System Prompt 尾端加入以下強制規則：

System Prompt 尾碼約束 
# CRITICAL OUTPUT RULES（必須嚴格遵守）
1. 只輸出純 SQL 語句。
2. 絕對禁止輸出任何 Markdown 標籤（如 ```sql 或 ```）。
3. 絕對禁止輸出任何說明文字、標題或前言。
4. 輸出的第一個字元必須是 SQL 關鍵字（如 SELECT、WITH 等）。
5. 預設加上 LIMIT 100 避免回傳過多資料。

三、SQL Query 插件（junjiem/db_query）設定

在 Dify 工作流中，我們推薦使用 Marketplace 上的 **junjiem/db_query:0.0.11** 插件作為資料庫連接媒介。以下是其核心參數配置：

Tool Parameters 
tool_parameters:
  db_type:
    type: constant
    value: mysql
  db_host:
    type: constant
    value: docker-db_mysql-1      # Docker 容器名稱（同 network 內可直接用服務名）
  db_port:
    type: constant
    value: 3306
  db_username:
    type: constant
    value: root
  db_password:
    type: constant
    value: <your_password>        # 建議用 Dify secret 管理
  db_name:
    type: constant
    value: erack                  # 目標資料庫名稱
  query_sql:
    type: mixed
    value: '{{#llm.text#}}'       # 直接引用 LLM 輸出
  output_format:
    type: constant
    value: markdown               # 輸出為 markdown 表格，方便前端渲染
ℹ️
Docker 網路 Host 設定技巧

若您的 Dify 容器與 MySQL 資料庫容器處於同一個 Docker 橋接網絡（Bridge Network）中，db_host 直接填寫 MySQL 的容器名稱（例如 docker-db_mysql-1）即可，無需填寫實體 IP。這能避免因 DHCP 重新分配 IP 導致的連線失敗。

四、踩坑紀錄：Code 節點的物件型別天坑

如果您在工作流中仍堅持使用 Code 節點來清洗 SQL，您將會遇到 Dify 變數封裝的隱性天坑：

  • TypeError: text.lastIndexOf is not a function：當您在 JavaScript 節點中直接對傳入的 llm_text 呼叫字串方法時，會拋出此錯誤。
  • result: "[object Object]"：為了修復錯誤，當您使用 String(llm_text) 進行轉型時，會發現得到的內容並非 SQL 而是 "[object Object]"。

根因剖析：Dify 在前端顯示的變數 {{#llm.text#}} 看似是純字串，但在 JS 沙箱的執行期，傳入 Code 節點的變數實際上是一個 Dify 內部定義的 Object Wrapper（對推理模型尤為明顯）。這會導致傳統的字串處理直接崩潰：

Code 節點編寫範例 
// ❌ 錯誤做法：直覺地將輸入變數轉換成 string
// 由於 Dify 在 JS 沙箱中傳入的是 Object Wrapper，這會得到字串 "[object Object]"
const cleanSql = String(input.llm_text).trim(); 

// ✅ 正確做法：若非得用 Code 節點，必須先印出其結構或利用 JSON 解析
// 更好的做法是：利用 System Prompt 約束 LLM 直接輸出乾淨 SQL，完全跳過 Code 節點
const cleanSql = input.llm_text.text || input.llm_text;

對策： 再次強調，最優解是完全跳過 Code 節點，直接將 LLM 的變數輸出 {{#llm.text#}} 綁定到 SQL Query 工具的 query_sql 參數上，從架構層面杜絕型別衝突。

五、AMR 搬送系統實務 Schema

在將資料庫 Schema 提供給 System Prompt 作為 Context 時，務必精簡。以下是 TSC AMR（erack）搬送系統的精簡對照表示意：

主要類別 主要資料表 常用業務規則與欄位約束
帳號與權限 user, account_type, permission user.enable = 1 代表啟用。
車輛（AMR） vehicle, vehicle_battery_info vehicle.enable = 1 且 vehicle.status = 'idle' 代表車輛閒置且可接收任務。
料架與載具 rack, carrier rack.status = 'up' 代表料架正常連線。
搬送指令與紀錄 transfer_executing_queue, order_command transfer_executing_queue 儲存正在執行的搬送任務。
