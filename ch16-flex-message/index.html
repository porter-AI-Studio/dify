第 16 章 · Part 5：整合開發

LINE Flex Message 整合

將 LINE Flex Message 模板資料庫化，配合 FastAPI 中介層進行執行期動態獲取，並探討 v1.0/v1.1 的安全性演進與 400 故障排除。

二、天坑背景：硬編碼在 DSL 中的 Flex JSON

在開發 LINE 機器人的過程中，我們經常需要回傳精美的 Flex Message。在早期的 Dify 整合模式中，整個多達數百行的 Flex JSON 字串是被直接「硬編碼（Hardcode）」在 Dify 工作流的 HTTP Request 節點裡。

這帶來了極其沉重的運維代價：

  • 每一次微調按鈕顏色、更改文字或新增一個按鈕，都必須手動修改並重新匯出、匯入整個 Dify DSL 檔案。
  • 難以進行版本控制與多人協作，開發人員極易在龐大且轉義複雜的 JSON 字串中出錯。
  • LINE 的 Channel Access Token 與測試者的 User ID 明文保存在 DSL 環境變數中，匯出時會造成嚴重的憑證外洩風險。

三、解決方案：模板數據庫化與中介 API

為了解決上述問題，我們對架構進行了全面重構：將所有 Flex 模板結構與 LINE 頻道憑證從 DSL 中剝離，遷移至地端 MySQL 中儲存，並使用 FastAPI 開發 flex-api 服務（運行於 Port 8002）在執行期動態調用。

1. 資料庫結構設計

我們在 MySQL line_flex 資料庫中建立了兩張資料表：

init.sql 
-- LINE Flex Message 模板表
CREATE TABLE flex_message_templates (
  id VARCHAR(64) NOT NULL PRIMARY KEY,
  description VARCHAR(255) NULL,
  contents JSON NOT NULL, -- 儲存 Flex 核心 Contents JSON
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

-- LINE 頻道憑證表 (v1.1 引入，杜絕 DSL 環境變數明文洩漏)
CREATE TABLE line_channels (
  name VARCHAR(64) NOT NULL PRIMARY KEY,
  channel_access_token TEXT NOT NULL,
  default_user_id VARCHAR(64) NOT NULL,
  description VARCHAR(255) NULL
);

2. flex-api 服務端點一覽

  • GET /flex：列出資料庫中註冊的所有模板清單（ID 與描述）。
  • GET /flex/{id}：獲取單一模板的完整 contents JSON 物件。
  • POST /flex：新增或覆蓋（Upsert）一個 Flex 模板。
  • GET /line/channel/{name}：獲取特定頻道的 Access Token 與預設 User ID（v1.1 引入）。

四、Dify DSL 工作流節點設計與演進

從 v1.0 到 v1.1，我們逐步消除了 DSL 內部的硬編碼，實現了安全性的閉環：

1. v1.0：基本模板獲取與組裝

工作流路徑為：Start ──> fetch_flex ──> assemble ──> send_line ──> Answer

  • fetch_flex (HTTP GET)：調用 http://flex_api:8000/flex/{#start.flex_id#}。
  • assemble (Code - Python3)：接收 API 返回的內容，並在程式碼中將其包裝成 LINE API 要求的包裹格式。
    Dify Code Node (組裝邏輯) 
    import json
def main(fetch_body: str, alt_text: str) -> dict:
    parsed = json.loads(fetch_body)
    # flex_api 已正規化回傳純 contents 物件，在此補齊 LINE 要求的包裹欄位
    msg = {
        "type": "flex",
        "altText": alt_text,
        "contents": parsed["contents"]
    }
    # 回傳 JSON 序列化字串給下方的 HTTP Node 傳送
    return {"messages_json": json.dumps([msg], ensure_ascii=False)}
  • send_line (HTTP POST)：調用 LINE 官方 Push 端點 https://api.line.me/v2/bot/message/push。

2. v1.1：憑證資料庫化（安全閉環）

在 v1.0 中，LINE API 金鑰依然儲存在 Dify 的環境變數裡。v1.1 則全面將其移入資料庫。工作流新增了兩個前置節點：

Start ──> fetch_line_config ──> extract_line_config ──> fetch_flex ──> ...
  • fetch_line_config (HTTP GET)：調用 http://flex_api:8000/line/channel/default。
  • extract_line_config (Code)：解析並提取 Token 與 User ID，徹底將憑證從 Dify DSL 檔案中刪除，完美實現解耦。

五、常見故障排除與踩坑經驗

在 Dify 中整合 LINE Flex 時，常遇到以下天坑，請嚴格遵守對應的解決方案：

1. LINE API 400 Error (messages[0] in the request body is invalid)

  • 根因：您的 Flex Message 被包裝了雙重嵌套。由於 flex-api 儲存的內容中若已經包含了外層的 "type": "flex"，而在 assemble 節點中又習慣性包裝了一次 "type": "flex"，導致結構變成了 flex -> contents -> flex。
  • 對策：flex-api 資料庫內應**僅存** carousel 或 bubble 物件，不應包含外層的 type:flex。同時在 API 返回層加入正規化防禦：若偵測到最外層是 type: flex，則自動將其 `contents` 提取出來覆寫。

2. Pydantic 序列化產生的 additionalProp1 多包一層

  • 根因：在呼叫 POST 註冊模板時，FastAPI 使用 Pydantic 的 response_model 進行自動序列化，如果設定不當會導致 JSON 被包裹進 additionalProp1 欄位中，造成 LINE 無法讀取。
  • 對策：直接使用 SQL 刪除該髒資料並重新插入，這是最乾淨的做法： 
    DELETE FROM flex_message_templates WHERE id='xxx';
INSERT INTO flex_message_templates (id, description, contents) VALUES ('xxx', '說明', '{"type":"carousel","contents":[...]}');

3. HeidiSQL 連線 access denied / public key retrieval 失敗

  • 根因：MySQL 容器安全設定只允許 localhost (127.0.0.1) 連接，若在 HeidiSQL 連接時填寫具體的局網 IP 會被拒絕。
  • 對策：主機名稱填 localhost（Port 13366）。且在 Advanced 標籤中務必勾選 allowPublicKeyRetrieval=true 並關閉 SSL，否則會報 Public Key 抓取錯誤。

4. flex_api 容器連不上 MySQL

  • 根因：Docker 容器網路隔離，flex_api 容器無法直接透過局網 IP 連上同台機器上的 MySQL 容器。
  • 對策：環境變數中的 MYSQL_HOST 必須填寫 Docker 內部的 **Hostname（即 MySQL 的服務容器名稱 db_mysql）**，且連線埠應填寫容器內部的 3306，而非對外映射的 13366。
