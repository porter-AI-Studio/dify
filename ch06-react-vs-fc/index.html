第 6 章 · Part 2：模型設定

ReAct vs Function Calling 深度解析

深入比較 ReAct 與 Function Calling 兩種 Agent 策略的原理、適用場景、錯誤模式與實務選型建議。

一、代理決策的兩大流派

在大語言模型（LLM）進化為 AI Agent 的過程中，最核心的挑戰在於「如何讓模型決定何時以及如何調用外部工具（如 API、資料庫、搜尋引擎等）」。為了解決這個問題，業界逐漸演化出兩大主要策略：ReAct（Reasoning and Acting） 與 Function Calling（工具調用）。

在 Dify 中，這兩種策略直接決定了 Agent 應用的執行邏輯、token 消耗以及整體運作的穩定性。了解這兩者的本質差異與優缺點，是設計一個高性能 AI Agent 的基石。

二、ReAct 策略：文字解析的思考迴圈

ReAct 是早期 Agent 的核心機制（由 Yao 等人於 2022 年提出）。它的核心思想是將推理（Reasoning）與行動（Acting）緊密結合。模型在回答問題前，會被引導按照特定的文字格式輸出它的思考過程。

ReAct 的運作流程通常為一個循環：

  1. Thought（思考）：模型用文字描述自己當前的想法與下一步計畫。
  2. Action（行動）：模型決定要調用的工具名稱。
  3. Action Input（行動輸入）：模型給出調用工具所需的參數。
  4. Observation（觀察）：系統執行該工具，並將結果回填給模型。
  5. 重複以上步驟，直到模型輸出 Final Answer（最終答案）。
ReAct 執行歷程範例 
Thought: 使用者詢問「今天台北幾度？」，我需要先查詢台北的天氣。
Action: get_weather
Action Input: {"city": "台北"}
Observation: {"temperature": "25°C", "condition": "陰天"}
Thought: 我已經取得天氣資訊，可以回答使用者。
Final Answer: 今天台北的氣溫是 25°C，天氣狀況為陰天。
ℹ️
ReAct 的限制

ReAct 完全依賴「文字正則表達式（Regex）」來解析模型輸出的純文字字串。如果模型在輸出時漏掉了關鍵前綴（例如漏了 Final Answer:），或是輸出了髒字元（例如多吐了 Observation），框架解析器就會失效，導致 Agent 陷入死循環或給出空白回應。

三、Function Calling 策略：API 原生的結構化呼叫

為了克服 ReAct 文字解析容易出錯的缺點，各大模型廠商（如 OpenAI、Anthropic、Google 等）推出了原生支援的 Function Calling（或稱 Tool Calling）。

此策略不再依賴模型輸出 Thought/Action 等文字標籤，而是透過 API 層級直接返回結構化的 JSON 欄位（通常在 response 中的 tool_calls 陣列）。模型在預訓練或微調階段，就已經學習了如何理解工具定義（Schema）並輸出符合該 Schema 的 JSON 參數。

OpenAI 相容之 tool_calls 回應結構 
{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": null,
      "tool_calls": [{
        "id": "call_weather_001",
        "type": "function",
        "function": {
          "name": "get_weather",
          "arguments": "{\"city\": \"台北\"}"
        }
      }]
    }
  }]
}

因為是由 API 機制直接保證輸出結構，Function Calling 具有以下顯著優勢：

  • 穩定性極高：極少發生因為模型漏字而導致解析失敗的狀況。
  • 節省 Token：模型不需要輸出冗長的「思考過程」文字，直接輸出工具參數，降低延遲並減少 Token 成本。
  • 並行呼叫（Parallel Tool Calls）：原生支持在單次推理中同時調用多個工具，而不需要跑多次 Thought 循環。

四、深度對比：ReAct vs Function Calling

以下整理了這兩大策略在各面向的詳細對比，作為您在 Dify 中設定 Agent 策略的參考：

比較面向 ReAct 策略 Function Calling 策略
工具呼叫機制 模型輸出純文字標籤，由框架正則（Regex）解析 模型直接輸出結構化 JSON，由 API 原生欄位承載
模型硬限制 任何 LLM 只要 Prompt 夠清晰皆可使用 模型必須經過 Tool Use 微調，且推理引擎須支援
輸出穩定性 中至低（格式易跑掉、容易漏 Final Answer） 極高（由 API Schema 強制規範）
Token 成本 較高（每次思考都要額外產生 Reasoning Token） 低（跳過思考文字，直達參數）
多工具並行 困難（通常一次只能跑一個 Thought-Action 循環） 原生支援單次並行（Parallel）呼叫多個工具
可讀性與偵錯 人類友善，可直觀看見 Agent 思考脈絡 機器友善，通常需要自己分析 Log 才能看到內部細節
Dify 對應策略 agent_mode.strategy: react agent_mode.strategy: function_calling
💡
生產環境首選

在實際生產環境中，Function Calling 已經是業界絕對的主流。ReAct 目前多用於教學展示、本地超輕量小模型（無工具微調），或是需要將 Agent 的思考歷程完整展示給用戶的特殊介面。

五、Dify 啟用機制與常見陷阱

在 Dify 中使用自架地端模型（如透過 openai_api_compatible 接入的 vLLM 或 Ollama）時，很多人會遇到「在 Agent 設計頁面中找不到 Function Calling 選項，只有 ReAct 可選」的問題。這通常是因為在註冊模型時忽略了以下特徵設定：

1. 新增模型時的必填設定

  • Function calling：必須滑到註冊對話框的底部，將此項從 Not Support 修改為 Tool Call。
  • Model context size：預設為 4K，請務必填寫模型真實大小（如 131072），否則會因長文本截斷導致 FC 失敗。
⚠️
新版 Dify「配置」按鈕無法修改特徵參數

目前新版 Dify 將 Function Calling 與 Context Size 等特徵參數鎖定在「新增模型」流程中。一旦模型註冊完畢，事後的「配置」按鈕僅能修改憑證與憑證綁定。如果您先前填錯了，唯一的補救方法是刪除模型，然後重新註冊。

2. NIM + Llama-4-Maverick 實戰踩坑案例

在實務測試中，我們曾嘗試在 NVIDIA NIM 平台註冊 meta/llama-4-maverick-17b-128e-instruct 模型並啟用 Function Calling。此模型在規格書上寫著原生支援工具調用，但我們在 Dify 中使用時卻失敗了，原因在於模型漏出了 assistant 角色 Token，且將 Tool Schema 渲染成文字 JSON 塞在 content 欄位中，而沒有寫入 API 層級的 tool_calls 欄位。

這說明了「模型支援 Function Calling」並不等於「該推理端點（Endpoint）的 API 實作完整」。在將模型接入 Dify 之前，強烈建議先使用 curl 模擬發送帶有 tools 參數的請求，檢查返回的 JSON 結構中是否確實包含 tool_calls 欄位，以判斷其相容性。

六、地端 Agent 部署與選型決策

如果您正在自建 vLLM 或 Ollama 推理服務，並希望為 Dify Agent 提供穩定的 Function Calling 能力，請參考以下建議：

1. vLLM 啟動參數與 Tool-Call Parser

在啟動 vLLM 服務時，必須啟用自動工具選擇並指定對應模型的解析器（Parser）：

vllm serve <model_path> --enable-auto-tool-choice --tool-call-parser <parser_name>

常見的解析器對應如下：

  • hermes：適用於 Qwen2.5-Instruct 系列、NousResearch 系列。
  • llama3_json：適用於 Llama-3.1 / 3.2 / 3.3 全系列。
  • phi4_mini：適用於 Phi-4-mini。

2. 地端模型選型建議

  • RTX 4090 (24GB) 預設首選：建議部署 Qwen2.5-14B-Instruct-AWQ (4-bit)，搭配 hermes parser。其 FC 成功率與中文理解能力在小模型中表現極為優異，可徹底根治 20B 以下舊模型（如 gpt-oss-20B）在 ReAct 模式下漏字或重複調用工具的病灶。
  • 雙卡或 L40S (48GB) 進階推薦：部署 Qwen2.5-32B-Instruct-AWQ (4-bit)，其 FC 準確度在中文場景能直接對標 Llama-3.3-70B。
  • 大型旗艦（A100 / H100 80GB）：首選 Llama-3.3-70B-Instruct-AWQ (4-bit)，配合 llama3_json parser，是目前地端 Agent 最穩定的業界標竿。
