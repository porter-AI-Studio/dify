名詞解釋 (Glossary)

解讀本書中使用的關鍵術語，建立統一的詞彙認知。

一、核心名詞釋義

1. Pipeline (管道)

定義：將複雜的 AI 任務拆解成多個明確步驟的流程引擎。

說明：
不同於傳統的單次模型呼叫（Single Model Call），Pipeline 透過資料流（Data Flow）將各個獨立節點串接起來，能夠應付複雜的業務自動化場景。

解決策略：

  • 模組化：替換或獨立優化特定節點。
  • 可視化：利用拖曳畫布定義執行拓撲。

2. NL2SQL (Natural Language to SQL)

定義：將使用者的自然語言提問轉換為可執行的資料庫查詢語句。

說明：
這是 Pipeline 極為經典的應用場景。系統需先判斷意圖，然後呼叫 LLM 產生 SQL，接著由資料庫執行，最終再轉譯為自然語言回覆，這中間常因為 Schema 太大而產生幻覺。

解決策略：

  • 利用工作流進行強制邏輯控制。
  • 使用大型 Schema 架構策略與分拆技術。

3. ReAct (Reasoning and Acting)

定義：一種讓大型語言模型交替進行「推理」與「行動」的 Prompting 框架。

說明：
在設計 Agent 架構時，ReAct 能讓模型先「思考」該採取什麼行動，接著調用工具（行動），並觀察結果再進行下一步推理。與單純的 Function Calling 不同，ReAct 具備強大的思考鏈。

解決策略：

  • 適合沒有原生支援 Function Calling 但具備強大推理能力的模型。
  • 配合系統 Prompt 規範以避免無限迴圈。

4. Function Calling (函數呼叫)

定義：模型原生具備的，能根據提問輸出符合 JSON Schema 的工具呼叫指令的能力。

說明：
相對於 ReAct 的 Prompt 引導，Function Calling 是模型在訓練時就被微調過的能力，能更穩定、更有效率地與外部 API 或工具（Tools）對接。

解決策略：

  • 優先使用支援原生 Function Calling 的模型來建置 Agent。
  • 精確定義工具描述（Tool Grounding）以避免誤調。

5. Model Context Protocol (MCP)

定義：讓 Agent（大腦）與外部工具（雙手）進行標準化通訊的開源協定。

說明：
透過 FastMCP 等伺服器，可將本地端的程式碼安全地封裝成 AI 可隨時調用的工具，實現安全的邊界控制與權限管理。

解決策略：

  • 標準化對接：統一各種 AI 工具的呼叫介面。
  • 內網穿透：搭配 Docker 網路實現本機端與容器間的通訊。

6. Asymmetric Routing (非對稱路由)

定義：網路封包的去程與回程路徑不一致，導致防火牆或 NAT 阻斷連線的現象。

說明：
在 Windows Docker 環境中，當容器透過 host.docker.internal 呼叫本機服務時，常因非對稱路由導致連線逾時（Timeout）。

解決策略：

  • Port Proxy：使用 Windows netsh interface portproxy 進行本機端口映射。
  • 網路層轉發：確保去程與回程皆經過同一個 NAT 代理。

7. Session Auth (會話認證機制)

定義：透過中介層管理使用者對談連線，避免敏感金鑰外洩的安全設計。

說明：
為了解決直接將 Dify API Key 暴露在前端的安全隱患，透過建立 Flask 代理層（Proxy）與 UUID 映射，實現的安全防線機制。

解決策略：

  • 代理轉發：前端只接觸 UUID，後端代理負責補上真實的 Dify API Key。
  • 持久化儲存：將 Conversation ID 對應儲存於資料庫，維持對話連貫性。

8. Object Wrapper (物件包裝器陷阱)

定義：變數在不同系統節點間傳遞時，被意外包裝成 JSON 物件而非純字串的型別問題。

說明：
Dify 工作流中極為隱蔽的雷區。當上游節點傳遞資料給 Code 節點時，若未經過嚴格轉型，傳入的會是帶有中介資料的 Object，進而導致程式碼執行崩潰。

解決策略：

  • Prompt 約束：在 LLM 節點就用 System Prompt 嚴格限制輸出純文字。
  • 跳過 Code 節點：儘量利用模型自身的 JSON Mode 輸出，減少手寫字串處理。

9. Loop Engineering (循環工程)

定義：取代傳統單次提示詞，利用「計畫→執行→驗證」自動閉環的 AI 開發範式。

說明：
透過 Maker-Checker 分離機制，讓 Agent 能夠自主反覆修正錯誤。系統包含 Automation、Worktree、Skills、Connectors 與 Sub-agents 五大模組。

解決策略：

  • 目標導向：設定明確可量化的結束條件。
  • 分離驗證：實作專門負責檢查成果的 Checker 節點。

10. CodeGraph / Git Nexus (專案知識圖譜)

定義：將龐大專案的程式碼解析為抽象語法樹 (AST) 與符號依賴關係的關聯資料庫。

說明：
幫助 AI Agent 獲取精準的「全局上下文 (Context)」，大幅降低 Token 浪費並避免盲目修改程式碼而導致的聯動錯誤。

解決策略：

  • 本地檢索：利用 SQLite FTS5 在本機快速索引與搜尋。
  • MCP 整合：作為 AI Agent 的動態 Context 供應端點。

二、名詞特徵對照表

術語 主要症狀 / 表象 影響 推薦策略
Pipeline 單次 Prompt 無法完成的複雜任務 提升系統可靠度，但增加了架構複雜度 將任務徹底解耦與模組化
NL2SQL 需要即時查詢資料庫的語意問答 SQL 容易因為幻覺而出錯或查不到資料 搭配大 Schema 拆解與工作流防錯
ReAct 需讓模型思考並試探解題步驟 推論過程透明，但消耗較多 Token 與時間 應用於無原生 FC 的強大模型中
Function Calling 需要精準對接外部 API 工具 直接返回 JSON 結構，效率與穩定度較高 為工具撰寫精準的描述（Grounding）
MCP AI 工具呼叫缺乏標準化介面 降低開發效率，整合困難 使用 FastMCP 封裝本地工具
Asymmetric Routing Windows Docker 內連線頻繁 Timeout 容器無法穩定調用本機 API 利用 netsh portproxy 穿透
Session Auth 前端直接存取 Dify API API Key 外洩，安全性極低 部署 Flask Proxy 與 UUID 映射
Object Wrapper Code 節點字串處理時意外報錯 工作流中斷，除錯困難 透過 Prompt 嚴格約束輸出格式
Loop Engineering 單次 Prompt 無法完成大型專案 依賴人工反覆介入修正 設計自動化驗證的循環架構
CodeGraph AI 修改程式碼引發未知的聯動 Bug Token 浪費且重構風險極高 建立並檢索 AST 依賴知識圖譜
