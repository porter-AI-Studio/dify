第 15 章 · Part 5：整合開發

Login-App（QA Bot Portal）開發

介紹 Dify 前台登入入口（QA Bot Portal）的 Flask/SQLite 架構、對話與 Session 持久化、與 DeepSeek 推理標籤實時過濾代碼。

一、為什麼需要 Login-App 中介層？

雖然 Dify 官方自帶了優美的 Web 對話介面，但它在企業落地時有幾個核心限制：

  • 無法與企業現有帳號整合：Dify 預設需要使用 Dify 後台帳號登入，無法輕易介接企業內部的 LDAP、AD 或是自訂的帳號驗證系統。
  • 安全性疑慮（金鑰暴露）：若前端直接以 Dify 的 API Key 進行請求，惡意使用者能輕易透過瀏覽器開發者工具攔截該 Key，盜用您的 LLM 額度。
  • 缺乏更細粒度的權限控管：無法針對不同使用者動態開放/隱藏特定的 Dify App。

因此，我們開發了 Login-App（又稱 QA Bot Portal） 作為中介 Proxy 層。它是一個基於 Python Flask + SQLite 的輕量服務，前端使用者僅與 Flask 進行驗證，Flask 再使用隱藏於環境變數中的 API Key 代理請求 Dify，實現完美的安全防護與權限控管。

二、系統架構與目錄結構

Login-App 透過 Docker 掛載，其 SQLite 資料庫以 Volume 方式持久化，確保容器更新時資料不遺失：

瀏覽器（LINE / Web） ──> Flask (Port 5050) ──> Dify API (Port 5001)
                             │
                             └──> SQLite (data/users.db)

在專案目錄結構中，templates/ 下分為了前台聊天與管理員後台（admin/）兩套範本：

  • app.py：主程式，負責所有 Session、路由控制與 API 轉發。
  • data/users.db：持久化 SQLite 資料庫。
  • templates/admin/：管理後台，供網頁端管理帳號權限與歷史問答匯出。

三、SQLite 資料庫設計與防護

Login-App 本地 SQLite 資料庫包含以下核心表格：

  • users（使用者）：userid (PK) 儲存員工工號或 Email，密碼使用 SHA-256 加鹽雜湊 儲存，保障安全性。
  • apps（應用設定）：儲存 Dify 應用的 slug（唯一代碼）、金鑰（支援中英/Debug/Demo 等多金鑰），以及 use_token（是否啟用 Token 閘道防護）。
  • user_app_access（權限白名單）：白名單模式，若無紀錄則預設為沙盒（全開放）。
  • user_conversations（對話持久化）：複合主鍵為 (userid, app_slug)，綁定 Dify 的 conversation_id。當用戶跨裝置重新登入時，能自動讀取該 ID 接續舊對話，而非每次都開新對話。
  • token_log（驗證憑證）：儲存暫存的 UUID Token 對應關係，供 Dify 工作流中的 HTTP Node 向此 Portal 反向查驗使用者身分。
  • message_feedback（意見回饋）：記錄用戶對對話的評分與不滿意具體原因，彌補 Dify 歷史 API 無法存原因的短板。

四、實時 Streaming 代理與 DeepSeek 思路過濾

Login-App 作為 Proxy，必須原封不動地支持 Dify 的 **流式響應 (Streaming)**。同時，在目前使用推理模型（如 DeepSeek-R1、Maverick 等）的場景中，模型輸出的思考過程（<think>...</think> 標籤內容）不適合直接展現給最終用戶，需要在 Proxy 層進行實時過濾。

以下是 Flask 實現實時串流代理、持久化 conversation_id 並實時過濾思考標籤的核心代碼：

app.py (Streaming Proxy) 
@app.route('/portal/chat/send', methods=['POST'])
def chat_send():
    user_id = session.get('user_id')
    user_query = request.json.get('query')
    app_slug = request.json.get('slug')
    
    # 根據 slug 獲取對應的 Dify API Key（支持中英/Debug/Demo 多金鑰路由）
    app_record = db.query("SELECT * FROM apps WHERE slug=?", (app_slug,))
    api_key = pick_api_key(app_record, session.get('lang'))
    
    # 調用 Dify 官方 App API
    dify_url = "http://api:5001/v1/chat-messages"
    headers = {
        "Authorization": f"Bearer {api_key}",
        "Content-Type": "application/json"
    }
    payload = {
        "inputs": {},
        "query": user_query,
        "response_mode": "streaming",
        "user": user_id,
        "conversation_id": get_user_conversation_id(user_id, app_slug) # 持久化綁定
    }
    
    response = requests.post(dify_url, json=payload, headers=headers, stream=True)
    
    def generate():
        in_think_block = False
        for chunk in response.iter_lines():
            if not chunk:
                continue
            line = chunk.decode('utf-8')
            if line.startswith('data: '):
                data = json.loads(line[6:])
                # 實時攔截並過濾 DeepSeek 等推理模型的 <think> 標籤
                text = data.get('answer', '')
                if '<think>' in text:
                    in_think_block = True
                    text = text.split('<think>')[0]
                if '</think>' in text:
                    in_think_block = False
                    text = text.split('</think>')[-1]
                
                if not in_think_block and text:
                    data['answer'] = text
                    yield f"data: {json.dumps(data)}\n\n"
                
                # 持久化更新 conversation_id
                if data.get('event') == 'message' and data.get('conversation_id'):
                    save_user_conversation_id(user_id, app_slug, data['conversation_id'])
                    
    return Response(generate(), mimetype='text/event-stream')

五、路由清單與對外驗證 API

Login-App 提供了完整的前後端路由與供 Dify 工作流回訪的 Token 查驗介面：

  • 前台登入與登出：GET/POST /portal/login、GET /portal/logout。支持 @gyro.com.tw 郵箱免密碼登入並繼承權限。
  • 對話代理：POST /portal/chat/send（代理發送）、GET /portal/chat/history（加載 Dify 歷史紀錄）。
  • Token 驗證入口：GET /portal/verify_token?token=<uuid>。當 Dify 處理敏感任務時，可發送 HTTP 請求回本 Portal 查驗該 Token 對應的真實 userid。
  • 管理員後台（/portal/admin/*）：包含 /admin/users（使用者 CRUD 與 CSV 匯出入）、/admin/apps（應用的金鑰配置）、與 /admin/chat_history（合併 Dify 問答歷史與本地回饋，支持 UTF-8 BOM CSV 匯出）。

六、UUID Token Gateway (HTTP 回查驗證)

當 Dify Agent 需要執行高權限操作（如：核准請假、查詢薪資）時，由於 Dify 本身並不認識企業內部的 User ID，我們需要一套信任機制。Login-App 提供了一套名為 Token Gateway 的反向查驗機制：

  1. 前端在發起請求前，會先向 Login-App 申請一組一次性的 UUID Token。
  2. 前端將此 Token 作為參數傳給 Dify。
  3. Dify 工作流中的第一個節點設定為 HTTP 請求，向 Login-App 的 /portal/verify_token?token=<uuid> 發送查驗。
  4. Login-App 驗證無誤後，回傳真實的 userid 供 Dify 進行後續的業務邏輯判斷。
Dify HTTP Request Node 配置重點 Security
✅ API Endpoint 設定
方法選擇 GET，URL 設定為 http://host.docker.internal:5050/portal/verify_token。因為 Dify 與 Login-App 同在一台主機的 Docker 環境內，必須透過 host.docker.internal 才能互相打通。
✅ Query Params 注入
新增一個 Query 參數，Key 為 token，Value 選擇變數插入 sys.query（假設前端將 UUID 放在 query 開頭）或是從提取節點中取出的變數。
⚠️ 錯誤處理 (Error Handling)
當 Token 偽造或過期時，Login-App 會回傳 401 錯誤。請確保在 Dify 工作流中，這條 HTTP 請求節點的 失敗分支 (On Error) 有導向一個「拒絕訪問」的回答節點，絕對不能讓流程默默繼續往下執行。
