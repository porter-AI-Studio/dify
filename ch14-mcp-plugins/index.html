第 14 章 · Part 4：Agent 開發

MCP 工具與插件接入

FastMCP 整合注意事項、DNS 重綁定保護關閉方式、SSE 連線設定，以及 junjiem/db_query 等 Marketplace 插件使用。

一、什麼是 MCP 與 Dify 插件？

Model Context Protocol (MCP) 是由 Anthropic 推出的開源協議，旨在提供一個標準化接口，讓大語言模型能安全、穩定地與地端資料來源或外部 API 進行通訊。

Dify 原生支持兩種方式來擴充 Agent 與工作流的能力：

  1. 外部自建 MCP Server：使用 Python 或 Node.js 開發，並以 SSE（Server-Sent Events） 協定掛載至公網或 Docker 內部網域，接入 Dify 作為自訂工具。
  2. Marketplace（插件市場）插件：直接安裝 Dify 生態系中的開源插件（例如常用的資料庫查詢插件 junjiem/db_query），快速實現開箱即用的外部整合。

二、FastMCP 與 Dify 整合的三大天坑與對策

當您使用 Python 的 FastMCP 框架編寫工具，並嘗試在 Docker 自架的 Dify 中接入時，極易遇到連線失敗的狀況。以下是實戰中總結出的三個關鍵配置要點：

1. DNS 重綁定保護（DNS Rebinding Protection）

FastMCP 預設啟用了安全性防護，會嚴格檢查傳入請求的 Host 與 Origin 標頭。

  • 問題現象：Dify 容器在調用位於主機上的 MCP 服務時，通常會使用 http://host.docker.internal:PORT/mcp/sse。因為主機名稱與 FastMCP 預期不匹配，會直接導致 FastMCP 後端報錯 ValueError: Request validation failed (400 Bad Request)。
  • 常見誤區：在 FastAPI 中設定 allowed_hosts = ["*"] 是無效的，因為該防護是在 FastMCP 底層的 TransportSecurityMiddleware 中處理，此中間件不支援 * 萬用字元。
  • 正確解法：在開發或 Docker 內網環境中，直接在腳本中關閉此防護：
Dify / FastMCP Server Logs
[ERROR] FastAPI Application Error
> Request: GET /mcp/sse
> Host: host.docker.internal:8000

ValueError: Request validation failed
at transport_security.py:45
"Host header 'host.docker.internal' does not match allowed hosts."
> HTTP/1.1 400 Bad Request
main.py (Hotfix)
from fastapi import FastAPI
from mcp.server.fastmcp import FastMCP

app = FastAPI()
mcp = FastMCP("MyService")

# FIX: Disable DNS Rebinding
mcp.settings.transport_security\
  .enable_dns_rebinding_protection = False

app.mount("/mcp", mcp.sse_app())
main.py (完整 FastMCP 整合配置) 
from fastapi import FastAPI
from mcp.server.fastmcp import FastMCP

app = FastAPI()
mcp = FastMCP("MyMCPService")

# 1. 關閉 DNS 重綁定保護，防止 Docker 中 host.docker.internal 400 Request validation failed
mcp.settings.transport_security.enable_dns_rebinding_protection = False

@mcp.tool()
def get_amr_status(vehicle_id: str) -> str:
    """查詢地端 AMR 的即時狀態"""
    return f"AMR {vehicle_id} 運作正常，電量 90%"

# 2. 將 MCP SSE 應用掛載到 FastAPI 上（記得括號執行 sse_app()）
app.mount("/mcp", mcp.sse_app())

2. FastAPI 掛載語法（Mounting）

在將 FastMCP 掛載到 FastAPI 上時，請確保語法為 app.mount("/mcp", mcp.sse_app())。請注意，mcp.sse_app() 必須帶括號執行，因為它是一個方法，呼叫後才會返回一個 ASGI 應用程式實例。

3. Dify SSE 工具連線設定

在 Dify Console 中新增自訂工具時，請按照以下規格填寫：

  • 連線類型：選擇 SSE (Server-Sent Events)。
  • URL 格式：使用 http://host.docker.internal:PORT/mcp/sse（假設掛載路徑為 /mcp）。
  • 動態註冊：務必關閉「使用動態客戶端註冊」。
  • 身分驗證：選擇 None。如果 Dify 依然驗證失敗，可在 API Key 欄位填入任意 dummy 偽造字串繞過。

三、Dify Marketplace 插件實戰：junjiem/db_query

在 Dify 中實現「自然語言自動生成 SQL 並執行（NL2SQL）」時，最推薦且最簡潔的工作流設計模式為：

開始 ──> LLM 生成 SQL ──> SQL Query (junjiem/db_query) ──> Answer 輸出

💡 最佳實踐：最簡原則（極重要）

只要 LLM 的 System Prompt 含有嚴格的輸出約束（例如禁止輸出 ```sql Markdown 標記、僅輸出純 SQL 文字），工作流中就不需要加入 Code 節點進行後處理。多一個中間節點就多一個出錯點，保持架構簡潔是提升 NL2SQL 成功率的關鍵。

1. SQL Query 插件參數配置

將 junjiem/db_query:0.0.11 安裝後，將其拖入工作流中，引數配置如下：

Dify SQL Query Tool 參數配置 
# Dify 中 SQL Query 節點的參數配置
db_type: mysql
db_host: docker-db_mysql-1   # 與 Dify 同一個 Docker Network 時可直接用容器名稱
db_port: 3306
db_username: root
db_password: your_secret_password
db_name: erack
query_sql: "{{#llm.text#}}"  # 直接引用上游 LLM 生成的純 SQL 字串
output_format: markdown      # 輸出格式設定為 markdown，方便前端直接以表格渲染
ℹ️
Docker 網路連線技巧

如果 Dify 與您的 MySQL 資料庫都運行在同一個 Docker Network 中，db_host 可以直接填寫 **MySQL 的容器名稱**（例如 docker-db_mysql-1），Dify 內部 DNS 會自動解析，無需填寫複雜的 IP 地址。

2. 避開 Code Node 型別轉換陷阱

如果您的工作流確實需要使用 Code 節點（JavaScript/Python）來清洗 LLM 生成的 SQL，請務必提防型別轉換問題：

在 Dify 中，上游 LLM 的輸出 llm.text 有時會以「Dify 內部 Object Wrapper」的形式傳入 Sandbox 中，而非標準的 primitive string。如果您直接呼叫 llm_text.trim() 等字串方法，會直接噴錯：

TypeError: text.lastIndexOf is not a function

如果您用 String(llm_text) 進行包裝以防止噴錯，則會得到 "[object Object]" 字串，這會被當成 SQL 傳給資料庫，導致 Query SQL can only be a single SELECT statement 語法錯誤。

對策：若必須使用 Code 節點，請先使用 JSON.stringify(llm_text) 印出其內部結構以取得真實的字串 Property，或儘量使用「最簡原則」，透過 Prompt 限制直接將 LLM 的 text 串接到 SQL Query 節點。

四、將業務邏輯寫入 MCP Tool 內部

將規則（Rules）直接寫入 MCP 工具的 docstring（Description）中，比寫在 Agent 的 System Prompt 裡更具擴充性（此技術稱為 Tool-Level Grounding）。例如在請假系統工具中：

  • 在 create_leave 的 docstring 中寫入業務邏輯：「正常工時為 09:00~17:00，午休 12:00~13:00 不計入請假，日期一律使用 ISO 8601 格式」。
  • 當 LLM 讀取到此工具 Schema 時，會自動遵循這些限制，而不需要在 Dify System Prompt 中層層堆砌，這能顯著降低全局 Token 的負擔。
