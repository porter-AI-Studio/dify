工程規範與開發哲學

本章節詳細說明 Dify 與 Antigravity 生態系專案的工程規則（Antigravity Rules），涵蓋命名規範、技術棧架構、測試規範與 Windows 環境適配。

💡
核心開發哲學

「規則不是為了限制自由，而是為了讓工程決策變簡單。能自動化的，不靠人記；能標準化的，不靠經驗。」

一、語言與輸出約定

為了確保程式碼在國際化與本地化開發中保持高可讀性，我們制定了嚴格的語言邊界約定：

  • 文件與說明：所有回覆、說明、系統設計文件、註釋以及 Walkthrough 成果報告，必須使用繁體中文。
  • 程式碼識別符：程式碼中的所有變數名稱、函數名稱、類別名稱、模組名稱一律使用英文，禁止使用中文拼音或不具備語意的縮寫。
  • 日誌與例外處理：所有拋出的錯誤訊息（Exception Message）、系統日誌（Logger）、print 輸出內容，強制使用英文，以便於在生產環境中進行自動化日誌解析。
  • 文件署名規範：所有產出文件中，若含有 **整理人：** Antigravity AI，一律改寫為 **整理人：** Antigravity AI & Porter，體現人機協作的核心精神。

二、Technology Profiles (技術路線)

在 Antigravity 專案中，一個專案只能選擇並遵循一個 Technology Profile，嚴禁跨技術棧混用。這能確保專案在維護過程中，技術棧不會無限制地膨脹。

Profile 技術棧名稱 典型適用場景
Profile A 前後端分離（預設） 企業級系統、微服務、高度客製化後端。
Profile B Next.js 全端專案 SaaS 產品、快速驗證的 MVP 專案。
Profile C 靜態簡易網頁 Landing Page、技術文檔書籍（如本指南）。
Profile D Odoo 客製化開發 企業 ERP 系統與工作流模組客製。
Profile E Blazor 全端專案 .NET / C# 微軟生態系企業內部系統。
Profile F ASP.NET Core Web API RESTful API 後端專案。
Profile G RAG 知識庫系統 基於 LangChain / LCEL 的檢索增強生成系統。
Profile H Dify 生態系統開發 Dify 核心、自定義插件、DSL 0.6.0 工作流開發。
Profile I n8n 自動化流程 自定義節點與複雜自動化工作流開發。
Profile J SSR + 現代介面 以 Flask/FastAPI 搭配 Jinja2 + Vanilla JS 與 Custom CSS（玻璃擬態、深色模式）的管理後台。

1. Profile J 技術棧細節規範

若啟用 Profile J，必須嚴格遵守以下限制：

  • 後端：Python 3.10+（Flask 或 FastAPI）。
  • 前端模板：Jinja2。
  • 前端樣式：Bootstrap 5 搭配客製化 CSS（實作 Glassmorphism 玻璃擬態與 Dark Mode 主題適配）。
  • 前端邏輯：使用原生 Vanilla JavaScript (ES2022+)，禁止在 HTML 模板中直接堆積超過 100 行的 Javascript 代碼（超過者必須拆分至獨立 .js 檔案）。

2. 專案宣告宣告

每個 Repository 的根目錄 README.md 必須包含明確的宣告，指示該專案所使用的 Profile：

README.md 
## Project Profile
- Technology Profile: Profile H

三、通用命名規範

專案檔案與程式碼識別符的命名格式，必須遵循下表的約定：

類型 命名規範 正確範例 錯誤範例
變數 / 函數 camelCase (駝峰式) getUserInfo(), lotHistoryList get_user_info(), UserInfo
類別 / 元件 PascalCase (大駝峰) MachineController, DocsLayout machine_controller, docsLayout
常數 UPPER_SNAKE_CASE (全大寫底線) MAX_RETRY_COUNT, API_BASE_URL maxRetry, api_url
檔案 / 資料夾 kebab-case (小寫連字號) ch20-engineering-rules.astro ch20_engineeringRules.astro

四、資料庫命名規範

在設計關係型資料庫的 Schema 時，為了維持實體關係的清晰與命名一致性，我們制定了以下規則：

  • 資料表 (Tables)：強制使用複數名詞，代表該表為多個資料實體的集合。例如 employees, machines, lot_history。
  • 欄位 (Columns)：強制使用單數名詞，對應資料表中的單一屬性。例如 employee_id, machine_name, start_time。
  • 主鍵 / 外鍵 (Keys)：
    • 主鍵命名：pk_<table_name>，或簡寫的主鍵欄位名稱 <table_singular>_id。
    • 外鍵命名：fk_<table_name>_<referenced_table_name>。
MySQL Schema Example 
CREATE TABLE employees (
    employee_id INT AUTO_INCREMENT PRIMARY KEY,
    employee_name VARCHAR(100) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE lot_history (
    history_id INT AUTO_INCREMENT PRIMARY KEY,
    machine_id INT NOT NULL,
    status VARCHAR(50),
    CONSTRAINT fk_lot_history_machines FOREIGN KEY (machine_id) 
        REFERENCES machines(machine_id)
);

五、測試規範與 AAA 模式

高品質的測試是程式碼重構與持續集成的基石：

  1. 核心邏輯強制測試：Domain Services、關鍵 Utils 工具函數等核心商業邏輯，如果沒有對應的單元測試，禁止提交合併 PR。
  2. AAA Pattern 測試結構：測試案例必須結構化，嚴格遵循 Arrange (準備) → Act (執行) → Assert (驗證) 模式：
tests/test_employee.py 
def test_add_employee():
    # Arrange: 準備資料與環境
    new_emp = Employee("John")
    
    # Act: 執行測試目標函數
    result = db.add(new_emp)
    
    # Assert: 驗證結果符合預期
    assert result.id is not None
    assert result.name == "John"

六、日誌與異常處理

為了確保在出現故障時能夠迅速定位問題，日誌必須結構化：

  • 標準日誌格式：[時間戳] 等級 模組名稱 - 訊息內容
app.log 
[2026-02-12 17:00:00] INFO MachineController - Machine M123 started
[2026-02-12 17:05:23] ERROR OrderService - Order #999 created failed: Insufficient stock
⚠️
例外處理安全防護

嚴格禁止使用裸 try-except: pass (Catch All) 來吞掉錯誤。必須捕獲具體的 Exception 類型，並記錄對應的錯誤日誌或向上拋出，以避免潛在的異常靜默失效。

七、地端推理模型預設

在 Dify 地端專案或工作流測試中，若需調用本地開源 LLM，預設使用 **gpt-oss:20b** (基於 Ollama 或 vLLM 推理引擎)。除非專案在需求規格中明確指定其他複雜分析模型（例如 GPT-4o 或 Claude 3.5 Sonnet），否則應當優先使用預設的地端模型以節約 API 權杖成本並確保資料隱私。

八、Excel 操作規範

在涉及自動化生成與解析 Excel 報表時，必須遵循視覺化與公式化的標準：

  • 工具選用：強制使用 excel-mcp-server 進行 .xlsx 檔案的讀寫與格式化，避免自行撰寫脆弱的臨時 Python 腳本。
  • 視覺強化：創建新的報表時，表頭（Header）必須設定為粗體，且背景色應設定為標準藍色（如 HEX：4472C4）搭配白色文字，以提升可讀性。
  • 公式優先：所有涉及數據關聯與彙整的計算（如加總、查找等），應優先使用 Excel 原生公式（如 =SUM(), =VLOOKUP()），維持報表的動態計算能力。

九、Windows 環境特定規範

在 Windows（win32）環境下執行 Python 腳本時，控制台（CMD/PowerShell）預設的編碼常因為不支援 UTF-8 而導致 Emoji 或 Unicode 特殊字符輸出崩潰（UnicodeEncodeError）。

強制要求：凡是涉及 CLI 互動或 UI 輸出的 Python 腳本，在其程式進入點必須加上以下編碼修正處理：

main.py 
import sys
import io

if sys.platform == 'win32':
    sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding='utf-8', errors='replace')
    sys.stderr = io.TextIOWrapper(sys.stderr.buffer, encoding='utf-8', errors='replace')
