版本升級與備份管理

升級前先備份，出錯時有退路——建立可重複的維運節奏

一、資料存放在哪裡？

Dify 所有持久化資料都儲存在 Docker Volume 中，不在容器內部。 容器刪除後，Volume 中的資料仍會保留——這是安全升級的基礎。

二、升級前備份

升級前務必備份這三類資料。向量資料可以重新 Embedding（但耗時耗費）， PostgreSQL 資料（對話、Workflow、帳號）無法自動重建，一旦損毀就是永久遺失。

備份 PostgreSQL

# 建立備份目錄
mkdir -p ~/dify-backup

# 執行 pg_dump（在 db 容器內執行，輸出到主機）
docker compose exec db pg_dump -U postgres dify > ~/dify-backup/dify-db-$(date +%Y%m%d).sql

# 確認備份檔案存在且不為空
ls -lh ~/dify-backup/

備份 Volumes（完整快照）

# 備份 Weaviate 向量資料
docker run --rm \
  -v docker_weaviate_data:/source:ro \
  -v ~/dify-backup:/backup \
  alpine tar czf /backup/weaviate-$(date +%Y%m%d).tar.gz -C /source .

# 備份上傳的原始檔案
docker run --rm \
  -v docker_app_storage:/source:ro \
  -v ~/dify-backup:/backup \
  alpine tar czf /backup/storage-$(date +%Y%m%d).tar.gz -C /source .

備份 .env 設定檔

# .env 含有 SECRET_KEY 等關鍵設定，必須一起備份
cp dify/docker/.env ~/dify-backup/dot-env-$(date +%Y%m%d).bak
備份驗證：備份完成後，確認三個備份檔都存在且大小合理。 一個空的 .sql 檔是常見失誤（往往是容器名稱錯誤），請在升級前確認。

三、執行升級

Dify 的升級流程是：拉取新的 Git commit → 拉取新的 Docker Image → 重啟容器。 重啟後 api 服務會自動執行 Alembic 資料庫 migration。

升級流程
① 執行備份（上一節）
↓
② git pull（取得最新 compose 設定）
↓
③ docker compose pull（下載新 Images）
↓
④ docker compose up -d（重建容器）
↓
⑤ api 自動執行 Alembic migration ✓
cd dify

# 1. 取得最新程式碼
git pull

# 2. 進入 docker 目錄，拉取新 images
cd docker
docker compose pull

# 3. 重建並重啟所有服務（保留 volumes）
docker compose up -d

# 4. 觀察 api 啟動 log，確認 migration 成功
docker compose logs -f api

在 api 的 log 中，看到類似以下輸出即代表 migration 完成： 

INFO  [alembic.runtime.migration] Running upgrade ...
INFO  [alembic.runtime.migration] Done
INFO  Starting gunicorn 22.0.0
INFO  Listening at: http://0.0.0.0:5001

四、Migration 失敗的處理

若升級後 api 服務反覆重啟，最常見原因是 Alembic migration 出錯。 此時不要慌張，按以下步驟排查： 

# 查看完整錯誤訊息
docker compose logs api | grep -A 5 "ERROR\|FAILED\|alembic"

# 若確認是 migration 問題，先停止服務再還原資料庫
docker compose down
# 接著執行下一節的還原流程
v1.8.1 已知問題：Celery Worker 也會在啟動時嘗試執行 Alembic migration。 若多個服務同時競爭，可能導致衝突。建議升級時先讓 api 單獨完成 migration 再啟動其他服務：

docker compose up -d db redis && sleep 5 && docker compose up -d api && sleep 10 && docker compose up -d

五、還原備份

若升級後發現嚴重問題，需要回滾至備份狀態： 

# 1. 停止所有服務
docker compose down

# 2. 啟動 db，等待就緒後還原
docker compose up -d db
sleep 8

docker compose exec -T db psql -U postgres -c "DROP DATABASE IF EXISTS dify;"
docker compose exec -T db psql -U postgres -c "CREATE DATABASE dify;"
docker compose exec -T db psql -U postgres dify < ~/dify-backup/dify-db-20240101.sql

# 3. 還原 Weaviate 向量資料
docker run --rm \
  -v docker_weaviate_data:/target \
  -v ~/dify-backup:/backup \
  alpine sh -c "rm -rf /target/* && tar xzf /backup/weaviate-20240101.tar.gz -C /target"

# 4. 還原上傳檔案
docker run --rm \
  -v docker_app_storage:/target \
  -v ~/dify-backup:/backup \
  alpine sh -c "rm -rf /target/* && tar xzf /backup/storage-20240101.tar.gz -C /target"

# 5. 切回舊版 git tag，重啟
git checkout v1.x.x
docker compose up -d

六、鎖定版本，避免意外升級

若要穩定運行，建議在 .env 中明確指定使用的 Image 版本， 而非預設的 latest tag： 

# .env 中加入版本鎖定（以 1.3.0 為例）
DIFY_VERSION=1.3.0

搭配 Git tag 管理，讓每次升級都是有意識的決策，不會因為 docker compose pull 意外取得 breaking change。查看可用版本：git tag -l | sort -V | tail -20

七、建立雙環境自動化備份排程

為了達成可重複且可靠的維運，我們提供了針對 Local 與 AWS 兩種環境的 PowerShell 備份腳本。這比單純備份資料庫更加全面，它同時囊括了 PostgreSQL、Weaviate 向量庫、Storage 原始檔以及至關重要的 .env 變數。

⚠️

.env 檔案的安全性： 您的 .env 包含了資料庫密碼與各種 API Keys。當腳本將 .env 納入 .tar.gz 備份壓縮檔時，請務必確保該備份目錄具備嚴格的存取權限，避免敏感金鑰外流！

環境類型 執行腳本 排程方式 保留天數策略
Local (Windows) backup-dify-local.ps1 Windows 工作排程器 (每日) 本機預設保留最近 7 天
AWS EC2 Gyro backup-dify-aws-gyro.ps1 Cron Job 或自動化 Pipeline EC2 備份檔 3 天 / S3 長期封存
💡

還原前強制備份機制： 無論是 Local 或是 AWS EC2 環境，我們的還原腳本 (restore-dify-local.ps1 等) 在覆蓋現有資料庫前，都會先強制進行一次 pre-restore 備份。這是防止「手滑覆蓋錯版本」的最後一道防線。
