第 1 章 · Part 1：入門

什麼是 Dify？架構與生態系

從零認識這個改變 AI 應用開發方式的開源平台——它的設計哲學、技術堆疊與完整生態系

一、Dify 是什麼？

Dify 是一個開源的 LLM 應用開發平台（Large Language Model Application Development Platform）， 目標是讓開發者與非技術人員都能快速將 AI 模型整合進真實產品，而不必從零建構提示詞工程、 RAG 流水線、Agent 邏輯或監控系統。

它的核心主張是「不重複發明輪子」：把資料接入、工作流程編排、模型切換、使用量追蹤這些 通用基礎設施統一處理，讓開發者專注於業務邏輯本身。

二、技術架構總覽

Dify 採用前後端分離架構，後端以 Python Flask 為核心，前端為 Next.js + React， 透過 Docker Compose 將所有服務打包，讓本地部署只需一行指令。

後端為何選 Flask 而非 FastAPI？

這是社群常見的疑問。Dify 團隊的取捨是穩定性優先：Flask 搭配 Gunicorn 的 gevent worker 可以在不修改任何同步 IO 程式碼的情況下實現高並發，降低早期開發時因非同步程式碼引入的 bug 風險。 而真正需要非同步的重型任務（文件索引、模型批次推論），全部交給 Celery 處理。

三、向量資料庫支援：23+ 種後端

Dify 以 Factory Pattern 封裝向量資料庫的存取介面，讓 23 種以上的實作可以無縫切換。 部署者只需修改環境變數，無需改動應用層程式碼。

四、三種版本：Cloud、Community、Enterprise

Dify 提供三種部署形態，Community 與 Enterprise 使用完全相同的 Docker Image， 差異僅在於啟動時的 Runtime 授權與環境變數。

五、Plugin 生態系（v1.0 Beehive 架構）

Dify v1.0 是一個重大里程碑：整個平台從「模組耦合」轉向「Plugin-First 架構」（代號 Beehive）。 在此之前，模型接入與工具呼叫是硬編碼在核心程式庫中；v1.0 之後，它們全部被解耦為獨立插件包， 可透過插件市集安裝，也可自行開發。

5 種 Plugin 類型
Models
接入各家語言模型（OpenAI、Claude、Gemini、Ollama 等），統一呼叫介面
Tools
可被 Agent 呼叫的外部工具（搜尋、計算機、資料庫查詢、第三方 API）
Agent Strategies
自訂 Agent 推理策略（ReAct、CoT、ToT 等），替換預設推理迴圈
Extensions
HTTP Webhook 擴充點，讓外部服務接入 Dify 的事件流（如發送通知、寫入資料庫）
Bundles
將多個 Plugin 打包為一個安裝單元，方便企業統一分發

Plugin 執行模式

插件本體由獨立的 dify-plugin-daemon 程序管理，支援 4 種執行模式：

本機 Subprocess
開發與輕量自架環境，Plugin 以子程序形式運行於同一主機
Debug（TCP + Redis）
本機開發除錯，透過 TCP 連接至遠端 Dify 實例測試插件
AWS Lambda
Serverless 模式，適合需要水平擴展的 Python 插件
企業私有部署
Enterprise 版支援私有 Plugin Runtime，符合合規隔離需求
注意：dify-plugin-daemon 的 Kubernetes 水平擴展（Scale-Out）目前有已知限制—— 雖有內部 clustering 機制，但多副本場景下的協調尚不成熟，建議生產環境先使用 Lambda 或單副本模式。 詳見官方 README。

六、生態系模組概覽

圍繞 Dify 核心，本書涉及的生態整合模組包含：

login-app
自架的獨立登入入口服務（Flask），提供表單驗證、JWT 發行，繞過 Dify 原生的帳號申請流程， 讓管理員完全掌控使用者存取。本書第三部分詳細說明。
flex-api
輕量 API Proxy 層，負責在 Dify 後端與前端通訊之間插入授權檢查、使用量限速、 多租戶 key 路由。本書第四部分說明架構設計。
LangBot
基於 Python 的對話機器人框架，可接入 LINE、Telegram、Discord 等即時通訊管道， 並以 Dify Workflow 或 Chatbot 作為 AI 後端。本書第五部分整合說明。
